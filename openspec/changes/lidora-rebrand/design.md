## Decisions

Use `Lidora` for display names, `lidora` for public machine names, `https://lidora.app` for the hosted canonical origin, `X-Lidora-*` for custom proxy headers and `LIDORA_DATA_DIR` for self-hosting. Keep neutral API paths, bindings (`DB`, `POLL_DB`), scopes and `X-Sync-Key` unchanged. Do not add old-header aliases, environment fallbacks or dual writes.

Retain the existing Worker identity, D1 resources (`sift-sync`, `sift-poll`, including IDs), SQLite filenames (`sift-sync.sqlite`, `sift-poll.sqlite`), volume mounts and persistent development directory. These are deliberate stable storage/infrastructure identifiers, not compatibility layers. Select IndexedDB `lidora` on the hosted `lidora.app` origin (and its local-only `.localhost` test origin); established origins and self-hosted installations continue using `sift`. Do not probe for databases or dual-write. Document retained identifiers in one place.
The existing abstract RSS app icon can remain if visual review confirms it has no letter S; replace the sidebar's literal s mark with a Lucide icon. Keep the established visual style. This is a rename, not an unrelated redesign.

## Browser migration

Changing the hosted origin creates separate browser storage. Pairing and OPML alone are insufficient: server sync does not represent every local article/body/preference. Existing same-origin installations retain their database and require no storage migration. Only the domain transition needs a low-friction transfer.
For the hosted origin change, browser security prevents lidora.app from reading the previous origin's IndexedDB directly. The old-origin app opens a dedicated receiver page on lidora.app from the user's “Move to Lidora” action. A Chromium prototype verified that the user-opened cross-origin window retains its opener and can establish a `MessageChannel` after checking the exact origin and window source. Use that direct channel with a fresh handshake; never put library data in URLs, use wildcard `postMessage` targets or send it through a public relay. Send bounded, acknowledged chunks and verify a SHA-256 digest before the receiver writes. The receiver validates the complete snapshot and reconciles it with any destination library in one readwrite transaction over all seven stores, then reads every store back and verifies its digest. Keep destination tabs paused until the source confirms its final snapshot still matches; only then unlock them and allow sync to start. A failed or interrupted transaction leaves the destination unchanged; retry repeats the verified merge. Do not report cross-browser acceptance until the same journey has been exercised in supported browsers and installed PWAs.

Capture all seven stores (feeds, items, itemBodies, meta, itemFlags, feedStats, readMarkers), including pending local state and settings. Inventory other origin storage and cached absolute URLs during implementation. Lock the source app in the initiating tab and every open tab running the new client before taking one readonly multi-store snapshot. Validate schema and relationships before writing, import atomically, and leave the source untouched on failure. Retry must be idempotent. For conflicts, match feeds by exact URL; merge matching feeds and their items/flags/bodies/statistics/markers, and remap source IDs when a destination ID collision belongs to another URL. Preserve all non-conflicting metadata and local sync queue entries; combine settings without replacing destination-only keys, preferring source values for conflicting preferences and retaining source sync credentials/cursors for continuity with the same server account. If the destination is paired to another sync account, keep that account's credential and cursors in a local recovery metadata record while the source account remains active. Never overwrite a destination library or ask users to discard one. Ensure sync does not start until migration completes; reconcile sync cursors and pending markers against preserved server data. Never put sync credentials or private feed URLs in URLs or logs.

Keep old-origin migration access available for returning users, including devices that were offline at launch. Do not retire it simply because known active users have migrated or a fixed recovery window has elapsed. Record a retirement decision only after accounting for remaining users and providing a durable recovery route. Installed PWAs should guide users through the transfer; explain any browser-required reinstall step. Do not redirect the old origin before transfer is possible. Remove migration code only when doing so cannot strand existing data. A clean final identity must not take priority over preserving user libraries.

Provide a full-library local backup/import recovery path as well. Backups may contain private feed URLs and account credentials; explain this when exporting. Validate failures, interrupted transfers, repeated migration, existing destination libraries, offline returning devices and installed PWAs before rollout.

## Server data and infrastructure

Keep both domains routed to the same existing Worker and D1 resources during transition. Inventory bindings, secrets by name, routes, schedules, rate-limit namespaces, OAuth settings and Workers Builds triggers before changing configuration. There is one account store and one polling scheduler; no D1 copy, binding swap, resource rename or branding-driven write freeze is required. Back up server data as normal release preparation.

Attach lidora.app to the current Worker. Separate routing/domain activation from making it the advertised primary origin. Continue using the documented deployment scripts with their existing D1 targets. Check per-origin CORS/proxy guards and service-worker routing explicitly: migration pages must work on both origins without allowing arbitrary origins. Old-origin requests may continue during transfer against the same authoritative data; after a device completes transfer, prevent its old app from continuing independent local edits.

For SQLite, change the configuration variable to LIDORA_DATA_DIR but point it at the same existing directory and preserve filenames, /data mounts and Docker volume identities. Document configuration/image upgrade and verify restart reuses the data; do not rename or recreate volumes because examples change. Preserve the Vite persistent directory. No server data-copy migration is part of this rebrand.

## Protocol and OAuth cutover

Rename every producer, consumer, allowlist, cached metadata key and assertion for `X-Sift-*` together. Change User-Agent to `Lidora/<version> (+https://lidora.app/about)` and synthetic failure-cache origin to `https://lidora.invalid`. Discard/rebuild disposable response caches rather than interpreting old internal headers.

MCP metadata becomes `lidora` / `Lidora`; generated setup instructions use the new URL. Set hosted `PUBLIC_URL` to the canonical origin and verify discovery, protected resource metadata, audience/issuer validation and connection approval. Treat old client registrations/grants as requiring reauthorization at the new origin. Determine explicit invalidation/cleanup from the OAuth implementation before deployment, while preserving reader accounts and sync state. Do not redirect authenticated MCP or OAuth exchanges across origins or accept old audiences as a fallback.

## Repository, distribution and documentation

Target repository `davegarvey/lidora` and image `ghcr.io/davegarvey/lidora`; check availability/access before executing remote renames. GHCR publication derives its path from `github.repository`, so coordinate repository rename, Actions permissions, package linkage, release credentials/rulesets, Workers Builds and local remotes. Publish and pull the new image before advertising it. Remove obsolete CLI instructions from maintained guidance without introducing a replacement CLI. Preserve legally meaningful operator/contact details.

Update package/lockfile name, docs, generated metadata, fixtures and all current OpenSpec requirements. Do not edit applied SQL migration bodies merely to remove historical comments. Archived OpenSpec, past releases and Git history remain historical records. Reconcile any still-active proposals so archiving them cannot restore old names. The final residual-name audit must explain every remaining match; permitted exceptions are immutable history, the documented retained storage/infrastructure identifiers, and migration access needed by returning users.

## Release and recovery

Use a conventional breaking-change commit/PR marker supported by the existing release workflow; verify its bump detection before merge. Let automation select the next major version; never manually bump or run grubble locally. Deliver one rebrand release on the existing infrastructure, followed by a controlled domain cutover. Before publishing the rebrand release, verify the complete migration journey on the new origin. Keep advertised URLs and OAuth issuer configuration appropriate to the active phase; do not advertise new-origin MCP setup until it is usable. The new domain may serve receiving/preview routes before it becomes primary.

Gate primary-domain cutover on successful browser transfer checks, server account continuity, OAuth reconnect and retained Settings UX. Once ready, advertise lidora.app, switch canonical/issuer metadata coherently and guide existing users through transfer. Keep old-origin migration access for returning users. Rollback must retain new-domain data and the same D1 resources: revert application/configuration only where compatible, never restore an old database snapshot over newer writes. Preserve a route to recover any library already transferred.

## Implementation prerequisites

Record repository/image availability, build-trigger behavior, dual-origin routing/guard behavior, OAuth transition details and browser-transfer acceptance criteria before cutover. These are implementation prerequisites, not reasons to move server storage. Refresh the branch against merged Settings work before implementation. Completion means the public identity and primary domain are Lidora, data continuity is verified, and old-origin recovery remains available where required; it does not require deleting retained internal names.
